Search strategies evaluation

Strategies are evaluated along the following dimensions:

  • Completeness: does it always find a solution if one exists?
  • Optimality: does it always find a least-cost solution?
  • Time complexity: number of nodes generated/expanded. We are interested in the worst-case scenario.
  • Space Complexity: maximum number of nodes in memory.

Time and space complexity are measured in terms of:

  • b – maximum branching factor of the search tree
  • d – depth of the least-cost solution
  • m – maximum depth of the state space (may be ∞)

Uninformed vs. Informed Search

  • Uninformed Search: uninformed strategies use only the information available in the problem definition (see Lab 01).
  • Informed Search: informed strategies have information on the goal state, which helps in more efficient searching. This information is obtained by a function (heuristic) that estimates how close a state is to the goal state.

Heuristic

📐 Definition

A heuristic h(n) is a function that estimates the cost (or distance) from a given state n to a goal state. It provides problem-specific guidance to search algorithms to prefer more promising states and reduce the search effort.

  • Heuristics are the driving force that allows estimation of distance to goal states — they're functions that take in a state as input and output a corresponding estimate.
  • The computation performed by such a function is specific to the search problem being solved.
  • With heuristics, it becomes very easy to implement logic in our agent that enables it to “prefer” expanding states that are estimated to be closer to goal states when deciding which action to perform.

A concrete example — two heuristics for the 8-puzzle — follows in Choosing a heuristic.

Beam Search (Local Beam Search)

= greedy best-first search with queue limit l, i.e., keeps only the l best nodes in the queue.

Complete?
No
It is a local search — the goal can be pruned away.
Optimal?
No
Time complexity
O(bml)
l nodes × b successors, repeated for m levels.
Space complexity
O(bl)
Linear space.
Data structure
Limited priority queue (size l, by h(n))

Why O(bml) time?

At every level the algorithm does the following:

  • Expansion: the algorithm only expands the l nodes selected from the previous level.
  • Generation of Successors: each of the l nodes generates b successors (children). The total number of new candidates generated at this level is l × b.
  • Heuristic Evaluation / Scoring: the algorithm calculates the score h(n) for all l · b candidates. This step takes time proportional to O(l · b).
  • Pruning (Selection): the algorithm selects the best l candidates out of the l · b total to carry forward to the next level. Sorting or selection takes time, often O(l · b log(l · b)) if sorting is done, or faster if efficient selection algorithms (like Quickselect or a min-heap) are used. In many common search contexts, this selection step is often simplified or amortized, or assumed to be minor compared to the expansion cost, leading to the linear complexity.

Overall time complexity: since the process is repeated for m levels, the total time complexity is O(m · l · b).

A*

A* and optimality of A*

Idea: avoid expanding paths that are already expensive.

  • Evaluation function f(n) = g(n) + h(n)
    • g(n) = cost so far to reach n
    • h(n) = estimated cost from n to goal
    • f(n) = estimated total cost of path through n to goal
📐 Admissible heuristic — A* requires it

A* search uses an admissible heuristic, i.e., h(n) ≤ h*(n), where h*(n) is the true cost from n. (Also require h(n) ≥ 0, so h(G) = 0 for any goal G.) A heuristic h(n) is admissible if it never overestimates the true cost of reaching the goal state G from any node n.

E.g., hSLD (straight-line distance) never overestimates the actual road distance.

Step through A* on the lecture graph. Each frontier entry shows g, h and f = g + h, and A* always expands the entry with the lowest f. Unlike greedy (cost 26), A* returns the optimal path S → A → D → F → G with cost 23.

Let C* be the cost of the optimal solution:

  • A* expands all nodes with f(n) < C*
  • A* expands some nodes with f(n) = C*
  • A* expands no nodes with f(n) > C*

Theorem: A* Search is Optimal

  • If h(n) is admissible, A* using TREE-SEARCH is optimal.
  • If h(n) is consistent, A* using GRAPH-SEARCH is optimal.
    • Optimality: a consistent heuristic guarantees that once a node is expanded, its cost will not be improved upon. Thus, the path found by A* will be the shortest possible.
    • Efficiency: because consistent heuristics prevent the re-expansion of nodes, they help reduce unnecessary evaluations, leading to a more efficient search process.

If h(n) is consistent, then it is also admissible; however, the converse is not necessarily true.

Proof (admissible h, tree search)

Suppose some suboptimal goal G2 has been generated and is in the queue. Let n be an unexpanded node on a shortest path to an optimal goal G1.

1
f(G2) = g(G2) — the actual path to G2, since h(G2) = 0
2
f(G2) > g(G1) — since G2 is suboptimal
3
f(G2) > g(G1) ≥ f(n) = g(n) + h(n) — since h is admissible
⇒
Since f(G2) > f(n), A* will never select G2 for expansion.

Lemma: A* expands nodes in order of increasing f value

  • A heuristic is consistent if h(n) ≤ c(n, a, n′) + h(n′)
  • If h is consistent, we have:

f(n′) = g(n′) + h(n′) = g(n) + c(n, a, n′) + h(n′) ≥ g(n) + h(n) = f(n) hence f(n) is nondecreasing along any path.

Admissible vs. consistent heuristics

To summarize, a heuristic is:

📐 Admissible

h(n) ≤ h*(n) for all n, where h*(n) is the true cost from n to the goal state — it never overestimates.

📐 Consistent

h(n) ≤ c(n, n′) + h(n′) for all n and every successor n′ — the heuristic can drop by at most the step cost.

  • Proof strategy for admissibility: the most common way to prove admissibility is to construct the heuristic as the exact solution to a relaxed problem. A relaxed problem is one where some constraints on the actions are removed, making the path cost to the goal necessarily less than or equal to the cost in the original, more constrained problem.

h(n) = Optimal cost in the relaxed problem ≤ Optimal cost in the original problem = h*(n)

  • A heuristic h(n) is consistent if, for every node n and every successor n′ generated by an action with cost(n, n′), the estimated cost to the goal from n is no greater than the cost to get to n′ plus the estimated cost from n′. The mathematical definition is: h(n) ≤ cost(n, n′) + h(n′).
  • Rearranging this gives the key insight that the drop in the heuristic value must be less than or equal to the actual move cost: h(n) − h(n′) ≤ cost(n, n′).
  • Proof strategy for consistency: to prove consistency, you must check the inequality for every possible single step from any node n to its neighbor n′. This usually involves showing that the move action is constrained such that the heuristic can decrease by at most the step cost.
  • Key relationship: any consistent heuristic is also admissible (assuming h(G) = 0). Proving consistency is sufficient to prove admissibility.

The optimal path from S to C is S–A–B–C with a total cost of 4. However, with A* graph search:

  • After starting from S, the options on the frontier are S–A with a cost plus heuristic of 1 + 3 = 4, or S–B with a cost plus heuristic of 3 + 0 = 3. So, we choose to explore S–B.
  • Next, the options on the frontier are S–A with f = 1 + 3 = 4, or B–C with a backward path cost of 5. So, we choose to explore S–A.
  • We've already reached B from the earlier path, so we don't consider edge A–B. Thus, our only option is to explore B–C for a cost of 5.
  • So, we will choose the path S–B–C with a total cost of 5, which is not optimal.

Tree Search

  • In tree search, a closed set is not needed because nodes are not revisited; there's no way to reach the same node via multiple paths.
  • The heuristic must be admissible, ensuring that A* will find the optimal path.

Graph Search

  • In graph search, a closed set is essential to avoid revisiting nodes through different paths (e.g., due to loops).
  • The heuristic must be both admissible and consistent to guarantee that A* finds the optimal path efficiently.
  • A consistent heuristic guarantees an optimal path even without a closed set, but reprocessing nodes can be inefficient.
  • An inconsistent heuristic can lead to excessive node expansions.
  • Using a closed set with an inconsistent heuristic can lead to suboptimal solutions.
  • A* with a consistent heuristic is optimally efficient.

More formally: the Manhattan distance

The Manhattan distance heuristic, hM(n), is the sum of the horizontal and vertical distances of every misplaced tile from its goal position.

📐 Manhattan distance

hM(n) = Σall tiles |current row − goal row| + |current column − goal column|

Admissibility proof for Manhattan distance

Relaxed problem: a tile can be moved to its goal position in one step, regardless of what other tiles or the blank space are doing.

  1. The true cost, h*(n), is the number of moves needed to move all tiles to their correct positions without collisions.
  2. The Manhattan distance hM(n) calculates the minimum number of unit steps required for each tile individually to reach its goal position, ignoring the presence of other tiles and the constraint of the blank space.
  3. Since the true problem requires a tile to wait for the blank space and potentially move other tiles out of the way, the actual number of moves h*(n) must be greater than or equal to the total minimum unit steps of all tiles.
  4. Therefore, hM(n) is a lower bound on h*(n):

hM(n) ≤ h*(n)

Consistency proof for Manhattan distance

Assume a move from node n to n′ by sliding the blank tile, which swaps positions with an adjacent tile, T. The step cost is cost(n, n′) = 1.

  1. The heuristic value hM(n) changes only for the tile T that was moved. All other tiles' distances remain the same.
  2. Since tile T was adjacent to the blank space, it moved one step closer to or one step farther from its goal position.
  3. Best case: if the move brings tile T one step closer to its goal, the Manhattan distance for T decreases by 1. ΔhM = −1 ⟹ hM(n) − hM(n′) = 1
  4. Worst case: if the move takes tile T one step farther from its goal, the Manhattan distance for T increases by 1. ΔhM = +1 ⟹ hM(n) − hM(n′) = −1

In all cases, the change in the heuristic value hM(n) − hM(n′) is ≤ 1. Since cost(n, n′) = 1, the consistency inequality is satisfied: hM(n) − hM(n′) ≤ 1 = cost(n, n′).

hM(n) ≤ cost(n, n′) + hM(n′)

You can check this in the puzzle above: every slide changes h₂ by exactly ±1.

IDA*

IDA* — Iterative Deepening A*

= combination between A* and iterative deepening search, i.e., uses the A* evaluation function f(n) = g(n) + h(n) as a threshold and runs DLS.

  • Each iteration is a depth-first search that prunes every node with f(n) > threshold.
  • The next threshold is the smallest f-value that was pruned in the previous iteration.

Iteration 1 — threshold = 2

  • Root node as current node, i.e. 2.
  • Threshold = current node value (2 = 2). So explore its children.
  • 4 > threshold & 5 > threshold. So, this iteration is over and the pruned values are 4 and 5.

Iteration 2 — threshold = 4

  • In pruned values, the least is 4, so threshold = 4.
  • Current node = 2 and 2 < threshold, so explore its children one by one.
  • First child 4: set current node = 4, equal to the threshold, so explore its children 5 and 4. 5 > threshold, so prune it; the second child 4 = threshold, so explore its children 8 & 7 — both > threshold, so prune them.
  • Similarly, explore the second child of the root, 5: 5 > threshold, so prune it.
  • So, our pruned values are 5, 8, 7 (and 5).

Iteration 3 — threshold = 5

  • In pruned values, the least is 5, so threshold = 5.
  • Current node = root = 2 < threshold, so explore its children one by one.
  • First child 4 < threshold: explore its children 5 and 4. 5 = threshold, so explore its children 7 & 8 — both > threshold, pruned. The second child 4 < threshold: explore its children 8 & 7 — both > threshold, pruned. Pruned so far: 7 & 8.
  • Explore the second child of the root, 5 = threshold, so explore its children 6 & 6 — both > threshold, pruned.
  • So, our pruned values are 7, 8 & 6.

Iteration 4 — threshold = 6

  • In pruned values, the least is 6, so threshold = 6.
  • Left subtree as before: 4 → 5 → 7 & 8 pruned; 4 → 8 & 7 pruned. Pruned so far: 7 & 8.
  • Second child of the root, 5 < threshold: explore its children 6 & 6, both = threshold, so explore them one by one.
  • The first 6 has children 6 & 8. 6 = threshold, so explore its children 13 & 7 — both > threshold, pruned. 8 > threshold, pruned. Pruned at this stage: 13, 7 & 8.
  • The second 6 = threshold: explore its children 7 & 9 — both > threshold, pruned.
  • So, our pruned values are 13, 7, 8 & 9.

Iteration 5 — threshold = 7

  • In pruned values, the least is 7, so threshold = 7.
  • First child 4 < threshold: its first child 5 < threshold, explore 7 & 8. 7 = threshold, so explore its children 12 & 14 — both > threshold, pruned. 8 > threshold, pruned.
  • Second child of 4, i.e. 4 < threshold: children 8 & 7. 8 > threshold, pruned; 7 = threshold, so explore its children 13 & 8 — both > threshold, pruned. Pruned so far: 12, 14, 8 & 13.
  • Second child of the root, 5 < threshold: explore 6 & 6. The first 6 has children 6 & 8; 6 < threshold, explore its children 13 & 7: 13 > threshold, pruned; 7 = threshold and it has no children. Then 8 > threshold, pruned.
  • The second 6 < threshold: explore 7 & 9. 7 = threshold, so explore its children 8 & 14 — both > threshold, pruned. 9 > threshold, pruned.
  • So, our pruned values are 12, 14, 8, 13 & 9.

Iteration 6 — threshold = 8

  • In pruned values, the least is 8, so threshold = 8.
  • Left subtree: 4 → 5 → 7 < threshold, explore 12 & 14 — pruned. 8 = threshold, explore 16 & 15 — pruned. Pruned so far: 12, 14, 16 & 15.
  • 4 → 8 = threshold, explore 12 & 9 — pruned. 7 < threshold, explore 13 & 8: 13 pruned; 8 = threshold and it has no children. Pruned so far: 12, 14, 16, 15, 9 and 13.
  • Second child of the root, 5 < threshold: explore 6 & 6 one by one. The first 6 has children 6 & 8; 6 < threshold, explore 13 & 7: 13 pruned, 7 < threshold with no children.
  • Next sub-child of 6 is 8 = threshold, so explore its children: 15 is the goal — found! The search stops; the second 6 is never visited.

Simulated Annealing

Simulated annealing escapes local maxima the opposite way hill climbing gets stuck: it allows some "bad" moves, accepted with probability exp(−Δ/T), and gradually cools T so bad moves become rarer over time.

–
P(accept worse move) = exp(−Δ/T)

High T, small Δ → almost always accept (explore). Low T, large Δ → almost never accept (settle). As T → 0 over time, this converges to hill climbing. Watch: simulated annealing

Research connections

These algorithms aren't just puzzle-solvers. Same three ingredients every time — search node, action, frontier/heuristic — applied to prompts, proofs, code, and molecules instead of grids.

Greedy / Best-First

Classical Planning with LLM-Generated Heuristics

Challenging the State of the Art with Python Code · NeurIPS 2025 · arXiv:2503.18809
Core idea
Instead of hand-crafting a planning heuristic, ask an LLM to write one as Python code; generate several candidates, keep whichever solves training problems fastest.
Problem
Domain-independent planning heuristics are hard to design by hand; letting the LLM output a full plan directly is unreliable on unseen tasks.
How the algorithm fits
Unchanged Greedy Best-First Search: states are planning states, actions are the domain's operators, and h(n) is literally the LLM-generated function ranking the frontier — GBFS still always expands the lowest-h(n) node.

LeanDojo: Theorem Proving with Retrieval-Augmented Language Models

ReProver is a theorem-prover LM: it repeatedly proposes the next proof "tactic," retrieving relevant lemmas from a huge math library to help decide.
Problem
Prior LLM theorem provers were unreproducible and bad at picking the right lemma from a large library.
How the algorithm fits
Search leaves grid-world entirely: a proof state is the search node, a tactic is the action, and best-first search explores the proof tree, expanding the state with the highest cumulative probability of its proof so far. Search isn't just for route planning.

Hill Climbing / Local Search

Gradient Coordinate Descent

classical optimization method, not a single paper
Core idea
Optimize one coordinate (variable) at a time, holding the rest fixed, choosing which coordinate to move next using gradient information — cycle until convergence.
How the algorithm fits
It is hill climbing in disguise: current point = search state, one-coordinate moves = the neighborhood, gradient magnitude = the heuristic for picking the next move.

Plum: Prompt Learning using Metaheuristic

Pan et al. · ACL Findings 2024 · 2024.findings-acl.129
Core idea
Finding a good LLM prompt is a search over a huge space of text strings. Plum tries six classic metaheuristics — including hill climbing and simulated annealing — to find human-readable prompts.
Problem
Prompt optimizers need to be automatic, discrete, black-box, gradient-free, and interpretable — most methods only hit some of these.
How the algorithm fits
A prompt is the search node; an LLM-based edit is the action; task accuracy is the heuristic/fitness. Hill climbing accepts a neighbor only if it scores higher, stopping when no neighbor improves.

PROTEGE: Prompt-based Diverse Question Generation from Web Articles

Puranik, Majumder, Chaoji (Amazon) · EMNLP Findings 2023 · 2023.findings-emnlp.362
Core idea
Generate many candidate FAQ questions from an article, then hill-climb over which subset to keep, balancing diversity and faithfulness to the source.
Problem
Automatically building a diverse, accurate FAQ knowledge base from long web articles.
How the algorithm fits
The search node is a candidate subset of questions; a move swaps one question in/out; the heuristic is a diversity+fidelity score; hill climbing keeps improving the subset until no swap helps.

Synthesizing Programmatic RL Policies with LLM Guided Search

Liu et al. · ICLR 2025 · arXiv:2405.16450
Core idea
Use an LLM to write a starting program (an interpretable RL policy), then run "Scheduled Hill Climbing" to keep improving it.
Problem
Searching program space for an RL policy from scratch takes tens of millions of environment interactions; an LLM can jump-start the search.
How the algorithm fits
A candidate program is the node; an LLM-guided edit is a neighbor; reward in the environment is the heuristic; a "schedule" controls exploration over time — hill climbing with a cooling-like control, close to simulated annealing.

Let's Revise Step-by-Step (ReLoc)

A Unified Local Search Framework for Code Generation with LLMs · NeurIPS 2025 · arXiv:2508.07434
Core idea
Instead of a big search tree of partial code, keep one candidate solution and repeatedly revise it, always keeping the best version seen so far.
Problem
Tree search over code is expensive; pure single-candidate revision struggles because pass/fail feedback is too coarse to tell good edits from bad ones.
How the algorithm fits
The node is the current best program; the neighborhood is LLM-generated revisions; a learned reward model replaces coarse pass/fail as the heuristic; the update rule is classic hill climbing — greedily keep the best-scoring neighbor.

Beam Search

Collaborative Beam Search

Enhancing LLM Reasoning via Collective Consensus · Xu, Ren, Zhang · EMNLP 2025 · 2025.emnlp-main.574
Core idea
Several different LLMs propose reasoning steps together; instead of a separate verifier model, the group's shared perplexity votes on which steps survive.
Problem
Single-model beam search for reasoning inherits that one model's blind spots and usually needs an expensive extra verifier.
How the algorithm fits
A partial reasoning trajectory is the node; the next step (from several LLMs) is the action; the beam keeps the top-B trajectories, scored by cross-model consensus instead of one learned verifier.

SOAR — Search or Accelerate

Confidence-Switched Position Beam Search for Diffusion Language Models · Cao et al. · ICML 2026 · arXiv:2602.10953
Core idea
Diffusion LMs greedily decide which masked position to reveal next; SOAR detects low confidence and temporarily switches to beam search over alternative reveal-orders, then switches back to fast greedy decoding once confident.
Problem
A single bad greedy commitment early on can lock a diffusion LM into a bad token order on hard reasoning problems — but always searching would be too slow.
How the algorithm fits
The node is a partially-unmasked sequence with a confidence score; the beam holds K candidates; low confidence triggers single-position beam branching, high confidence collapses back to parallel greedy decoding.

Panini: Continual Learning in Token Space via Structured Memory

ICML 2026 · arXiv:2602.15156
Core idea
New documents are converted into a growing graph of question-answer pairs; at query time, the system traverses the graph for the most likely multi-hop reasoning chain instead of re-reading raw text.
Problem
Standard RAG re-reasons over raw chunks repeatedly and can retrieve irrelevant context.
How the algorithm fits
A partial inference chain through the graph looks exactly like a beam-search state — but the abstract doesn't use the words "beam search" explicitly, so treat this one as a plausible, unconfirmed connection rather than a verified fact.

LLM Program Optimization via Retrieval Augmented Search (RAS)

Anupam, Shypula, Bastani · ACL Findings 2026 · arXiv:2501.18916
Core idea
Beam-search over candidate optimized rewrites of a slow program; at each step, retrieve similar past "slow → fast" examples and show them to the LLM as in-context guidance before it edits.
Problem
LLMs asked to speed up code with no guidance often produce mediocre or unsafe edits.
How the algorithm fits
A candidate program version is the node; a retrieval-guided LLM edit is the action; the beam keeps the top-B candidate versions by correctness/speed at every step.

A*

Path Planning using Neural A* Search

Yonetani, Taniai, Barekatain, Nishimura, Kanezaki · ICML 2021 · ICML page
Core idea
A CNN looks at a map and predicts a "guidance map" of which regions likely lie on the shortest path; A* then searches using that as its heuristic, made differentiable so the whole thing trains end-to-end.
Problem
Hand-designed heuristics (e.g. Euclidean distance) don't exploit learnable structure in real maps, causing excessive node expansion.
How the algorithm fits — the key point
A* itself is untouched: still f(n)=g(n)+h(n), still expands the lowest-f frontier node. The network does not replace A* — it only learns what A* uses as h(n).

KeeA*: Epistemic Exploratory A* Search via Knowledge Calibration

Zhao, Tu, Sun, Xu · NeurIPS 2025 · OpenReview
Core idea
A learned heuristic's error is itself uncertain. Instead of always expanding the lowest-f node (or sampling randomly), KeeA* clusters frontier nodes and uses the heuristic's own uncertainty to decide which clusters to explore.
Problem
Learned heuristics have systematic biases from limited training data; blind trust — or blind random exploration — both waste search effort.
How the algorithm fits
Same node/frontier/h(n) setup as A*, but node selection becomes a knowledge-calibrated, clustered sampling step instead of strict "always expand the minimum." Evaluated on retrosynthetic chemistry planning and circuit design.

Learning Admissible Heuristics for A*: Theory and Practice

Futuhi, Sturtevant · ICLR 2026 · arXiv:2509.22626
Core idea
Neural heuristics are powerful but usually aren't trained to respect admissibility. This paper's Cross-Entropy Admissibility (CEA) loss explicitly trains a network to stay admissible, with proven sample-complexity bounds for generalizing to new instances.
Problem
Learned heuristics can overestimate true cost, silently breaking A*'s optimality guarantee, with no guarantee they'll work on unseen problems.
How the algorithm fits
Directly next to this lecture: h(n) is a neural net trained to satisfy h(n) ≤ h*(n), which is exactly the condition that keeps A* optimal. Evaluated on Rubik's Cube against pattern-database heuristics.

FaSTA*: Fast-Slow Toolpath Agent with Subroutine Mining

for Efficient Multi-turn Image Editing · ICLR 2026 · arXiv:2506.20911
Core idea
An LLM plans an image edit as subtasks; a subtask matching a previously learned "subroutine" is reused instantly (fast path); a genuinely new subtask falls back to A* search over tool-call sequences (slow path), and successes get mined into new subroutines.
Problem
Re-running expensive tool search for every subtask — even repetitive ones — wastes cost; most subtasks aren't actually novel.
How the algorithm fits
The node is a partial toolpath applied to the image; the action is invoking one editing tool; A* searches this space, but only when no reusable subroutine already solves the subtask (reported: ~91% of tasks skip search entirely).
